# Feature: VDD Orchestrator

## Summary
A long-running, headless Rust orchestrator that drives crosslink issues through a deterministic Verification-Driven Development pipeline (implement → static QA → adversary → converge → land) using `claude-sandbox` workers in jj workspaces. The orchestrator owns all state transitions; agents produce artifacts only. The terminal step is mode-gated by crosslink's `tracker_remote` config: in local mode the orchestrator rebases the issue's change onto main and fast-forwards the bookmark; in remote mode it pushes the branch and opens a PR via `gh`. Conflicts in either path spawn a dedicated Merger agent. Crash-safe via file-backed state under the project bind; crosslink hub-branch replication and agent-key management are out of scope (crosslink-layer concerns).

## Requirements

- **REQ-1 (language/runtime + build system).** The orchestrator is a single Rust binary. Build system is **nix + cargo + just**: a `shell.nix` (classic nixpkgs invocation; dependencies pinned via **npins** in `npins/sources.json`) provides a dev shell with the toolchain (rustc, jj sources, claude-sandbox at a pinned commit, claude CLI, sqlite, python for hooks) plus the crosslink source and the jj source as npins-pinned sources exposed at stable paths; plain `cargo build` is the build driver; `just` exposes top-level recipes (`just build`, `just test`, `just orchestrate`, `just dogfood`); a `.cargo/config.toml` is generated by `just bootstrap` (or by the `shell.nix` `shellHook`) to inject the nix-provided source paths. Nix **flakes are deliberately avoided** — npins + a plain-nixpkgs `shell.nix` keeps the project composable with a non-flake `nixos-setup`. The crosslink dependency is wrapped in an insulation crate (REQ-3a); the jj dependency similarly (REQ-1c). Buck2 is explicitly deferred: revisit only if (a) we add a second language or (b) build times exceed 60s on a clean cache; that decision is recorded as a new issue, not a silent migration.
- **REQ-1a ("don't shell out" principle).** The orchestrator MUST use Rust libraries for every external operation except where no library exists OR where shelling out is the *contract* (e.g. user-supplied scripts). Concretely: jj operations *including git push/fetch* → `jj-lib` (REQ-1c) — `jj-lib`'s git interop is the only path to a git remote, there is no separate `gix`/`gitoxide` dependency; GitHub PR creation → `octocrab`; SQLite → `rusqlite` or `sqlx`; crosslink → `crosslink_api` (REQ-3a); terminal multiplexing for worker hosting/observability → zellij as a library (REQ-1d, scope TBD per Q6). Reasons: structured errors propagate through `?`, no string-parsing of stdout/stderr, no fork/exec per operation, type-safe arguments. **Allowed exceptions** (shell-out is correct): (a) spawning `claude` and `claude-sandbox` — no library exists; (b) `.orchestrator/static_qa.sh` — deliberately a shell script for per-project flexibility; (c) inside workers, `jj` is invoked as a CLI tool because Claude's tool surface is shell-based.
- **REQ-1b (rich errors via miette).** All orchestrator-side error types implement `miette::Diagnostic`. `thiserror` is used for enum definitions; `miette` provides labeled spans, related findings, and help suggestions. Errors bubbling out of `crosslink_api` and `jj_api` (REQ-3a, REQ-1c) carry source-location context so they render as compiler-style diagnostics in `events.jsonl` and on terminal output. `anyhow` MAY be used at binary entrypoints only, never in library crates.
- **REQ-1c (jj_api insulation crate).** Mirroring REQ-3a: an in-repo `crates/jj_api` crate wraps `jj-lib` and exposes a stable adapter surface for the operations the orchestrator performs (workspace add/forget, status, diff, log, rebase, bookmark create/move/list, git push, git fetch). Underlying `jj-lib` dependency path comes from nix (REQ-1). `jj-lib`'s API churn is contained to this crate. The Implementer (REQ-5) and Merger (REQ-19) still use the `jj` CLI inside their sandboxes — they cannot link Rust crates.
- **REQ-1d (zellij as worker host).** The orchestrator hosts every worker inside a zellij pane via `zellij-server`/`zellij-utils` Rust crates (no shelling out to the `zellij` CLI, consistent with REQ-1a). On startup the orchestrator either attaches to or creates a long-lived zellij session named `vdd-orchestrator` and tags it as headless (no attached client required). For each worker spawn the orchestrator creates a new pane in that session, names it `<role>-<issue>-r<round>` for findability, and launches `claude-sandbox` + `claude` inside the pane. Humans or other agents can run `zellij attach vdd-orchestrator` and switch to a pane to inspect a stuck worker live. Zellij is NOT used for observability dashboards in MVP — the existing triplet (heartbeat.json + events.jsonl + crosslink tui) remains the state interface. Zellij is NOT used to replace the heartbeat watchdog — `heartbeat.json` + `mtime` checks remain authoritative for staleness; pane lifecycle is a hosting concern, not a coordination one.
- **REQ-2 (state authority).** The orchestrator's authoritative state lives in `.orchestrator/state.db` (SQLite). Crosslink labels (`phase:*`, `round:N`) are a presentation layer; the orchestrator's next-action decision MUST read from `state.db` plus workspace artifacts, never from labels.
- **REQ-2a (in-flight substates).** Multi-step phases (`qa-gate`, `landing`) MUST track their internal progress in a `phase_substate` column. Defined substates: `qa_running`, `qa_passed_pending_transition`, `rebase_started`, `rebase_done_bookmark_pending`, `bookmark_moved_complete`, `push_started`, `push_done_pr_pending`, `pr_created`. On crash recovery the orchestrator MUST re-derive truth from the filesystem (jj log, bookmark position, `gh pr list`) before deciding whether to advance or repeat. Compile-time `cfg` choices MUST NOT determine routing between MVP and iteration-2 paths — routing reads `convergence_mode` from `.orchestrator/config.toml` at transition time. This prevents an issue persisted under MVP code from being misrouted by an iteration-2 binary.
- **REQ-3 (single writer to crosslink).** Workers MUST NOT mutate crosslink state. Workers produce structured artifacts in their workspace under `_orchestrator/`; the orchestrator parses artifacts against a schema and writes the corresponding typed comments (`--kind plan|decision|observation|blocker|resolution|result`).
- **REQ-3a (crosslink_api insulation crate).** The orchestrator never depends on crosslink's crates directly outside a single in-repo `crosslink_api` crate. `crosslink_api` re-exports the minimal symbol set we use (initially: issue read, comment write with `--kind`, signing, label add/remove) behind stable adapter functions whose signatures are owned by this repo. The underlying crosslink dependency path comes from the nix derivation (REQ-1) and pins a specific crosslink commit. Bumping the pin is an explicit operation tracked as an issue. When crosslink refactors break the build, the fix is localized to `crosslink_api`; the rest of the orchestrator does not move.
- **REQ-3b (worker DONE sentinel + idempotent translation).** Every worker, regardless of role, MUST write `_orchestrator/DONE` as its LAST filesystem operation. The file content is JSON: `{"exit_status": "success"|"error", "artifacts": [{"path": str, "sha256": str}]}`. The orchestrator treats absence of `DONE` as a crash regardless of process exit code (this catches partial-write torn-edge cases). Orchestrator-side, a `posted_artifacts` table (SQLite) keyed by `(worker_uuid, artifact_path, content_sha)` makes comment translation idempotent: each (worker, artifact-sha, finding-index) tuple posts at most once. Crash mid-translation → restart re-reads the artifact, skips already-posted tuples, posts the rest.
- **REQ-4 (sandboxed spawn).** Every worker is spawned via the existing `claude-sandbox` wrapper (bwrap) with `--permission-mode default` and an explicit per-role allowlist. `--dangerously-skip-permissions` MUST NOT be used. An unauthorized tool returns an error to the agent rather than prompting.
- **REQ-4a (pin claude-sandbox).** The `claude-sandbox` version is pinned by the `shell.nix` dev shell, whose `shellHook` captures the resolved store path into `VDD_CLAUDE_SANDBOX_PIN` at shell-entry. The orchestrator captures the expected version string in its config and refuses to spawn if `claude-sandbox --version` doesn't match (logs an `orchestrator-error` event and transitions affected issues to `phase:orchestrator-error`). Bumping the pin is an explicit operation tracked as an issue with a brief review of the diff for posture changes.
- **REQ-5 (jj-only worker VCS).** Workers see only `.jj/` in their workspace; `.git/` is never mounted into any worker sandbox. The Implementer's jj Bash allowlist permits `jj describe|commit|new|diff|show|log|status|files` and excludes `jj abandon|op undo|op restore|workspace forget|workspace add|workspace list|edit|git push|git fetch|rebase|squash|split`. (`jj squash` and `jj split` were dropped because they take a revision ID argument and the operation log is global — an Implementer could target another workspace's revision. They are not needed for "commit changes and exit.") The Merger's allowlist additionally permits `jj resolve|restore` plus read-only conflict-inspection commands. The orchestrator may run `jj git push` (via `jj-lib`) and `gh` itself from outside any sandbox during the landing step (REQ-17); workers never can.
- **REQ-5a (jj-repo serialization).** Because `.jj/` is a shared mutable namespace (commit graph, operation log, bookmarks visible across all workspaces), the orchestrator MUST hold a process-internal mutex around every operation that mutates `.jj/`: workspace add, workspace forget, rebase, bookmark move, push. Worker `claude` runtime itself is NOT serialized — workers spend most of their time editing files and only touch `.jj/` to commit at the end. MVP defaults: `max_per_role.implementer = 1`, `max_per_role.merger = 1`, `max_per_role.adversary = 2` (Adversary has no `.jj/` mount). Iteration 2+ may raise implementer concurrency once the serialization story is verified to not block real workloads.
- **REQ-6 (`.orchestrator/` invisibility).** The `.orchestrator/` directory is never bound into any worker sandbox. Physical isolation, not RBAC.
- **REQ-7 (`.crosslink/` read-only to workers).** Workers get a read-only bind of `.crosslink/` (memory, knowledge lookup, issue context). Writes fail at the filesystem layer.
- **REQ-8 (fresh-context phases).** Every Implementer round is a brand-new `claude` invocation. The orchestrator passes prior Adversary findings as a task input file, never as session memory. The Adversary similarly runs with fresh context, reading a pre-rendered `_orchestrator/diff.patch` and `_orchestrator/prior_findings.json`. No retry loop reuses an agent's session.
- **REQ-9 (QA gate determinism).** Static QA is `.orchestrator/static_qa.sh`, run by the orchestrator after every Implementer commit. The agent NEVER decides pass/fail. Exit-code 0 → `phase:adversary-review` (or `phase:converged` in MVP). Non-zero → captured tool name, exit code, last ~50 lines of output; posted as `--kind blocker`; orchestrator re-spawns the Implementer with that blocker as input.
- **REQ-9a (`jj-precommit` in the QA gate).** The `static_qa.sh` template that ships in the repo invokes `jj-precommit` — a wrapper that runs the `pre-commit` framework over the workspace's `trunk()..@` changed files — alongside the project's build/lint/test commands. `jj-precommit` is itself a shell script (no library form exists), so running it *from within* `static_qa.sh` keeps it inside REQ-1a's exception (b): the orchestrator never invokes `jj-precommit` directly, so no new orchestrator-side shell-out surface and no addition to the AC-24 lint's exception list. A non-zero `jj-precommit` exit is an ordinary QA blocker, handled exactly like a clippy failure (REQ-9). Prerequisites: `jj-precommit` and `pre-commit` must be on the dev-shell PATH (REQ-1), and the project must carry a `.pre-commit-config.yaml`.
- **REQ-10 (convergence orchestrator-owned).** Convergence is detected by the orchestrator from `findings.jsonl` emptiness + QA pass + round-N diff-hash stability, never declared by a worker. MVP ships with `mode = "n-rounds"`, `n_rounds = 2` defaults; `"judge"` and `"human"` modes are scoped but deferred.
- **REQ-11 (heartbeat watchdog).** Every spawned worker writes `<workspace>/_orchestrator/heartbeat.json` every ~10s via a PostToolUse hook. The hook source is `heartbeat.py` from crosslink's source tree (made available by the nix dev shell from REQ-1, NOT vendored into `.claude/hooks/`); just exposes it as a symlink or a generated wrapper at `.claude/hooks/heartbeat.py`. Updating crosslink (REQ-3a) automatically updates the hook. The orchestrator iterates active heartbeats each tick; stale > `heartbeat_threshold_s` → kill sandbox process group, `jj workspace forget` + `rm -rf` workspace, transition issue back to prior phase, re-spawn fresh.
- **REQ-12 (workspace lifecycle).** Spawn helper ALWAYS runs `jj workspace forget && rm -rf <workspace>` for an issue's workspace path BEFORE a fresh spawn, not only on success. Workspaces are named `.workspace/<phase>-<issue>-r<round>-<short-uuid>/` to permit multiple attempts on the same round.
- **REQ-13 (concurrency budget).** `[budget]` in `.orchestrator/config.toml`: `max_concurrent_agents`, `max_per_role` (defaults: `implementer = 1`, `merger = 1`, `adversary = 2`; see REQ-5a), `poll_interval_ms` (default 5000), `heartbeat_threshold_s` (default 120). Build pump waits at the "pick next issue" step when at cap; never queues at the agent level. `[turns]` section: `max_turns_implementer` (default 80), `max_turns_adversary` (default 40), `max_turns_merger` (default 30). A worker hitting its turn cap is treated like any other crash (no DONE sentinel → orchestrator re-spawns).
- **REQ-14 (observability triplet).** State is observable from outside the sandbox via: (a) `.orchestrator/heartbeat-<uuid>.json` per active worker, (b) `.orchestrator/events.jsonl` append-only (spawn, transition, QA result, watchdog kill, convergence), (c) `crosslink tui` / `crosslink issue show <id>` for narrative trail. No state lives anywhere not in this triplet.
- **REQ-15 (crash-safe resumption).** On orchestrator start, for every issue with a non-terminal phase: (a) inspect `phase_substate` (REQ-2a) to determine the in-flight step, (b) check the corresponding filesystem ground truth (`_orchestrator/DONE` sentinel from REQ-3b for worker phases; jj log + bookmark position + `gh pr list` for landing substates), (c) advance, repeat, or roll back based on a deterministic table documented in `crates/orchestrator/src/recovery.rs`. Specifically: a missing `DONE` for an in-flight worker phase ⇒ kill any surviving worker process, `jj workspace forget` + `rm -rf` workspace, transition issue to the phase prior to the worker spawn (e.g. `qa-gate` rolls back to `implementing`). For landing substates: `rebase_done_bookmark_pending` ⇒ check whether the bookmark has moved; if yes, advance; if no, retry the move. `push_done_pr_pending` ⇒ check `gh pr list` and either advance or retry. Recovery is idempotent: running the recovery routine twice produces the same final state.
- **REQ-15a (`phase:awaiting-human-merge` resumption).** This terminal-pending state is left only by a human action: applying the label `human-resolved:retry` causes the next poll to re-attempt the landing operation (skipping the Merger). The orchestrator does NOT poll for human signals beyond reading the issue label set each tick. If a human applies the label and the retry still fails, the issue returns to `phase:awaiting-human-merge` with a new blocker comment recording the second failure.
- **REQ-16 (refinement is out of scope).** The orchestrator does not run a Refinement pump. Issues are filed and decomposed by humans via `/design` and `crosslink subissue` interactively. The orchestrator picks up issues that are already at `phase:graphed` (or no phase, meaning "leaf-level, ready to implement" — see Q1 below).
- **REQ-17 (orchestrator-driven landing, mode-gated).** After convergence the orchestrator lands the issue's change without further human intervention. The mode is read from crosslink config `tracker_remote`:
  - **Local mode** (`tracker_remote` empty): orchestrator runs `jj rebase` of the issue's change onto current main, then fast-forwards the main bookmark. On success → `phase:merged`.
  - **Remote mode** (`tracker_remote` set): orchestrator runs `jj git push --bookmark issue-<id>`, then `gh pr create --base main --head issue-<id> --title "<jj description first line>" --body-file _orchestrator/result.md`. On success → `phase:pr-open`.
  - On rebase/push conflict in either mode → spawn a **Merger** worker (see REQ-19) and retry the landing step after the Merger completes. The orchestrator runs all jj operations (including `jj git push`, via `jj-lib`) and `gh` from outside any sandbox.
- **REQ-18 (cross-machine sync is out of scope).** Crosslink's hub-branch replication keeps `.crosslink/issues.db` in sync across machines. The orchestrator reads it and is otherwise oblivious to multi-machine. Hub-branch management, `crosslink agent init`, daemon setup, and trust approval are crosslink-layer concerns documented in the crosslink-guide.
- **REQ-19 (Merger role).** When `jj rebase` or `jj git push` fails with a conflict, the orchestrator spawns a Merger worker in a fresh jj workspace already in the conflicted state. The Merger sees `.jj/` (RW, mutex-guarded per REQ-5a), the workspace (RW), `.crosslink/` (RO), no `.git/`, no `.orchestrator/`. Its allowlist adds `jj resolve|restore` plus Read/Edit/Write. Input is `_orchestrator/conflict.md` (paths of conflicted files + the failing operation + the target). Output is `_orchestrator/merge_result.md` plus the resolution committed via `jj describe` (NOT `jj squash` — that's blocked for the same reasons as REQ-5). Worker writes `_orchestrator/DONE` last per REQ-3b. On Merger completion the orchestrator MUST: (1) re-run `static_qa.sh` on the post-merge tree, (2) only if QA passes, retry the original landing operation. If QA fails post-merge, treat it as Merger failure. Failure modes — missing DONE, non-zero exit, post-merge QA fail, retry-landing fail — all transition to `phase:awaiting-human-merge` (no further retries; see REQ-15a for the human-driven resumption path). In iteration 3+ the orchestrator may also re-spawn an Adversary on the merge diff before retrying landing; for MVP and iteration 2 the post-merge QA gate is sufficient.

## Acceptance Criteria

- [ ] AC-1: Repository builds via `nix-shell` + `just build`. `shell.nix` (npins-pinned) exposes a dev shell with rustc, jj, claude-sandbox (pinned), claude CLI, sqlite, python; `just bootstrap` generates `.cargo/config.toml` with the crosslink source path from the nix derivation; `just build` runs `cargo build --release -p orchestrator` and produces an executable at `target/release/orchestrator`. The `crosslink_api` crate compiles against the nix-vendored crosslink source. **(REQ-1, REQ-3a, REQ-4a)**
- [ ] AC-2: `.orchestrator/state.db` is created on first run via a SQLite migration in the binary. Schema is round-trippable: kill the orchestrator mid-tick, restart, and the in-flight state is reconstructed. **(REQ-2, REQ-15)**
- [ ] AC-3: Integration test: a worker that calls `crosslink issue comment` from inside its sandbox receives a "database is read-only" error; the local issue state is unchanged. **(REQ-3, REQ-7)**
- [ ] AC-4: Integration test: a worker spawned with `claude-sandbox` cannot read `.orchestrator/state.db` (file does not exist in its namespace). Verified with `ls .orchestrator || echo MISSING`. **(REQ-6)**
- [ ] AC-5: Integration test: an Implementer attempting `jj abandon` receives a permission error (not on allowlist); attempting `jj describe -m "x"` succeeds. **(REQ-5)**
- [ ] AC-6: Integration test: a worker invoked WITHOUT a `.git/` mount cannot run `git status` (binary or repo missing). **(REQ-5)**
- [ ] AC-7: `.orchestrator/static_qa.sh` is detected and executed after every Implementer commit. A test fixture project that fails `cargo clippy` keeps the issue at `phase:implementing` and posts a `--kind blocker` comment containing the clippy output's last ~50 lines. **(REQ-9)**
- [ ] AC-8: Integration test: spawn an Implementer, kill the `claude` process externally. Within `heartbeat_threshold_s + poll_interval`, the orchestrator detects the staleness, runs `jj workspace forget`, removes the workspace directory, transitions the issue back, and re-spawns. Confirmed via `events.jsonl`. **(REQ-11, REQ-12)**
- [ ] AC-9: `events.jsonl` records every state transition with `{ts, issue_id, from_phase, to_phase, worker_uuid, reason}` schema; `heartbeat-<uuid>.json` records `{ts, last_progress, current_op}`. Both are valid JSON parsable line-by-line / file-by-file. **(REQ-14)**
- [ ] AC-10: When `max_concurrent_agents = 1` and two issues are at `phase:graphed`, only one Implementer runs at a time; the second transitions only after the first completes (event log shows strict serialization). **(REQ-13)**
- [ ] AC-11a: **Fixture dogfood** (bootstrap, runs first): orchestrator runs against `tests/fixtures/hello/` (a separate tiny jj+crosslink repo committed into this repo's test data). File an issue ("Add a hello-world `say_hi` function with a passing test"), run the orchestrator with that fixture as its working directory, observe it producing a jj commit, rebasing onto main, fast-forwarding the main bookmark, and applying `phase:merged`. Done headlessly. This breaks the chicken-and-egg of the orchestrator self-modifying. **(MVP definition-of-done — covers REQs 1–9, 11–17 local path)**
- [ ] AC-11b: **Self-dogfood** (deferred until AC-11a passes): orchestrator runs against this very repo. File a similarly trivial issue (e.g. "Add a `vdd_say_hi` helper to `crates/orchestrator/src/lib.rs` with a passing test"), run the orchestrator, observe end-to-end landing on a fresh jj branch. Confirms the substrate works on the production target.
- [ ] AC-12: Remote-mode landing test on the fixture: with `tracker_remote = origin` and `gh` authenticated via a `GH_TOKEN` env var pointing at a test repository (test fixture documented in `tests/fixtures/hello/REMOTE_SETUP.md`). Orchestrator runs `jj git push` and `gh pr create`; the PR exists on the remote with body sourced from `_orchestrator/result.md`; issue transitions to `phase:pr-open`. **(REQ-17 remote path)**
- [ ] AC-13: Conflict-resolution test: pre-stage a fixture where the Implementer's change conflicts with main. Orchestrator's `jj rebase` fails, a Merger worker is spawned with `.jj/` and the conflicted workspace, the Merger resolves and commits, the orchestrator retries `jj rebase` successfully, issue transitions to `phase:merged`. Verified via `events.jsonl` showing the sequence `rebase_failed → merger_spawn → merger_complete → rebase_retry_ok`. **(REQ-19)**
- [ ] AC-14: Merger failure path: pre-stage a conflict the Merger cannot resolve (e.g. give it a 30s timeout via heartbeat threshold and a deliberately complex conflict). Orchestrator transitions issue to `phase:awaiting-human-merge` and stops; the issue carries a `--kind blocker` comment with the conflict context. **(REQ-19)**
- [ ] AC-15: After MVP (Iteration 2): integration test where Implementer commit produces a Rust file containing a deliberate `unsafe { ... }` block masked behind a safe-looking API; Adversary's `findings.jsonl` flags it; orchestrator translates to `--kind blocker`; Implementer round 2 receives the finding as input and removes it; round 3 Adversary produces empty findings; convergence detector transitions to `phase:converged` and then continues into the landing step. **(REQ-8, REQ-10, REQ-17)**
- [ ] AC-16: All orchestrator-side crosslink mutations are signed with the orchestrator's agent key; worker artifacts are translated by the orchestrator and attributed `role=<implementer|adversary|merger>` in the comment metadata. **(REQ-3)**
- [ ] AC-17: Crash-resilience test for `phase_substate`: spawn an Implementer that runs to completion, kill the orchestrator process between "worker exited" and "comments posted" by sending SIGKILL after detecting `_orchestrator/DONE`. On restart the orchestrator re-reads the artifacts, observes `posted_artifacts` table is empty, posts the comments exactly once, and advances. Re-running the recovery routine again is a no-op. **(REQ-2a, REQ-3b, REQ-15)**
- [ ] AC-18: Crash-resilience test for landing substates: kill the orchestrator between `jj rebase` and bookmark move (state shows `rebase_done_bookmark_pending`); on restart the orchestrator re-reads jj log, observes the bookmark is not yet moved, and completes the move. State advances to `bookmark_moved_complete → phase:merged`. **(REQ-2a, REQ-15)**
- [ ] AC-19: `claude-sandbox` version mismatch refusal: rename `claude-sandbox` to `claude-sandbox-wrong` (or substitute a version-faking shim) and start the orchestrator. It emits an `orchestrator-error` event, refuses to spawn any worker, and exits non-zero. **(REQ-4a)**
- [ ] AC-20: jj-repo mutex test: with `max_per_role.implementer = 2` set explicitly, two Implementers spawned for two different issues each call `jj describe` at the same moment. The orchestrator serializes the operations via its internal mutex; both succeed; `jj op log` shows the operations as cleanly sequential with no interleaved conflicts. **(REQ-5a)**
- [ ] AC-21: Post-merge QA gate: pre-stage a fixture where the Merger's `jj resolve` produces a syntactically valid but semantically broken result (a file that compiles but fails `cargo test`). Orchestrator's post-merge QA fails; issue transitions to `phase:awaiting-human-merge` with a blocker comment containing the test failure output. Retry does NOT happen automatically. **(REQ-19)**
- [ ] AC-22: Human-merge resumption: an issue in `phase:awaiting-human-merge` receives the `human-resolved:retry` label. On next poll the orchestrator attempts the landing operation directly (no Merger). If it succeeds → `phase:merged`; if it fails → back to `phase:awaiting-human-merge` with a new blocker. **(REQ-15a)**
- [ ] AC-23: DONE sentinel torn-write test: launch an Implementer that writes a half-line to `findings.jsonl` and dies without writing `DONE`. Orchestrator detects missing sentinel, treats as crash, cleans the workspace, re-spawns. The half-written `findings.jsonl` is never parsed as comments. **(REQ-3b)**
- [ ] AC-24: "No shell-out" hard lint (build-failing): a CI `xtask` (or `cargo deny` ban) fails the build if any non-test Rust file in `crates/orchestrator/src/**`, `crates/crosslink_api/src/**`, `crates/jj_api/src/**`, or `crates/error/src/**` contains `std::process::Command::new("jj")`, `Command::new("git")`, `Command::new("gh")`, `Command::new("crosslink")`, or `Command::new("zellij")`. The allowed exceptions are `claude-sandbox`, `claude`, and the `.orchestrator/static_qa.sh` path. **(REQ-1a)**
- [ ] AC-27: zellij-hosted spawn: integration test where an Implementer spawn produces a new zellij pane in session `vdd-orchestrator` named `implementer-<id>-r0`. `zellij list-panes` (only used in the *test* harness, not in non-test code) shows the pane is alive while the worker is running. The pane closes on worker exit. **(REQ-1d)**
- [ ] AC-25: `jj_api` integration test: workspace lifecycle (add → status → diff → describe → list) runs entirely through library calls; no `jj` subprocess is observable via `strace` during the test. **(REQ-1c)**
- [ ] AC-26: Error rendering: a forced QA-fail error rendered to terminal via `miette` shows the failing tool name, exit code, last lines of output, and the relevant `_orchestrator/result.md` path as labeled source spans. A forced jj-rebase conflict error similarly annotates the conflicted file paths. **(REQ-1b)**

## Architecture

### Repository layout

```
vetinari/
  shell.nix                       dev shell: toolchain + crosslink source + claude-sandbox pin
  npins/
    sources.json                  pinned nixpkgs / rust-overlay / crosslink / jj revisions
    default.nix
  justfile                        top-level recipes: build/test/orchestrate/dogfood/bootstrap
```

### Key data structures

**`state.db` schema (SQLite)**

```sql
CREATE TABLE issues (
  issue_id     TEXT PRIMARY KEY,            -- crosslink id, e.g. "L3" or "#42"
  phase        TEXT NOT NULL,               -- 'graphed' | 'implementing' | 'qa-gate' | 'adversary-review' | 'converged' | 'landing' | 'merged' | 'pr-open' | 'awaiting-human-merge' | 'orchestrator-error'
  phase_substate TEXT,                       -- REQ-2a: 'qa_running' | 'qa_passed_pending_transition' | 'rebase_started' | 'rebase_done_bookmark_pending' | 'bookmark_moved_complete' | 'push_started' | 'push_done_pr_pending' | 'pr_created' | NULL
  round        INTEGER NOT NULL DEFAULT 0,
  convergence_mode TEXT NOT NULL DEFAULT 'n-rounds',
  empty_round_streak INTEGER NOT NULL DEFAULT 0,
  -- empty_round_streak reset rules:
  --   reset to 0 when: (a) findings.jsonl non-empty in any round, (b) QA fails in any round,
  --                    (c) Implementer is re-spawned for any reason
  --   incremented when: a clean Adversary round produces 0 findings AND
  --                     last_diff_hash matches the prior round
  last_diff_hash TEXT,                       -- sha256 of jj diff for round-N stability check
  landing_retry_count INTEGER NOT NULL DEFAULT 0,  -- bounds the Merger spawn loop (max 1 per REQ-19)
  updated_at   INTEGER NOT NULL              -- unix seconds
);

CREATE TABLE posted_artifacts (              -- REQ-3b idempotent translation
  worker_uuid    TEXT NOT NULL,
  artifact_path  TEXT NOT NULL,
  content_sha    TEXT NOT NULL,
  finding_index  INTEGER NOT NULL DEFAULT -1,  -- per-finding for findings.jsonl; -1 for whole-file
  comment_id     TEXT NOT NULL,                -- crosslink comment id returned by crosslink_api
  posted_at      INTEGER NOT NULL,
  PRIMARY KEY (worker_uuid, artifact_path, content_sha, finding_index)
);

CREATE TABLE active_workers (
  worker_uuid  TEXT PRIMARY KEY,
  issue_id     TEXT NOT NULL,
  role         TEXT NOT NULL,                -- 'implementer' | 'adversary' | 'judge'
  round        INTEGER NOT NULL,
  workspace_path TEXT NOT NULL,
  pid          INTEGER,
  spawned_at   INTEGER NOT NULL,
  last_heartbeat INTEGER NOT NULL,
  FOREIGN KEY (issue_id) REFERENCES issues(issue_id)
);

CREATE TABLE events (
  -- mirrors events.jsonl; SQLite for query, JSONL for tail -f
  id           INTEGER PRIMARY KEY,
  ts           INTEGER NOT NULL,
  kind         TEXT NOT NULL,                -- 'spawn' | 'transition' | 'qa_result' | 'watchdog_kill' | 'convergence'
  issue_id     TEXT,
  worker_uuid  TEXT,
  payload      TEXT NOT NULL                 -- json
);
```

**Phase transitions (orchestrator-owned)**

```
phase:graphed
  └→ build pump picks → spawn Implementer → phase:implementing
       └→ Implementer commits + exits → phase:qa-gate
            ├→ QA pass → (MVP: phase:landing) | (it.2: phase:adversary-review)
            └→ QA fail → phase:implementing  (re-spawn fresh, blocker as input)
       └→ phase:adversary-review (it.2+)
            ├→ findings.jsonl non-empty → phase:implementing (re-spawn, findings as input, round++)
            └→ findings.jsonl empty
                  ├→ empty_round_streak < n_rounds → phase:adversary-review (re-spawn fresh Adversary)
                  └→ empty_round_streak >= n_rounds → phase:converged → phase:landing
       └→ phase:landing  (orchestrator runs from outside any sandbox)
            ├→ local mode: jj rebase + fast-forward main bookmark
            │    ├→ ok → phase:merged (terminal)
            │    └→ conflict → spawn Merger (REQ-19)
            ├→ remote mode: jj git push + gh pr create
            │    ├→ ok → phase:pr-open (terminal)
            │    └→ push conflict → spawn Merger (REQ-19)
            └→ Merger completes → retry landing operation
                  ├→ retry ok → phase:merged | phase:pr-open
                  └→ retry fails OR Merger failed → phase:awaiting-human-merge (terminal)
```

### Worker → orchestrator artifact contract

| Role         | Output artifact                  | Schema (parsed by `artifacts.rs`)                              |
|--------------|----------------------------------|----------------------------------------------------------------|
| Implementer  | `_orchestrator/result.md`        | freeform markdown — "what changed, what addressed from prior findings". Used as PR body in remote mode. Read post-phase only. |
| Implementer  | `_orchestrator/progress.jsonl`   | `{ts, op, detail}` per line; **OPTIONAL** appendable breadcrumb log. The orchestrator does NOT stream this to crosslink mid-phase (avoids partial-line read races). Read post-phase, summarized as one `--kind observation` per ~10 line cluster. |
| Adversary    | `_orchestrator/findings.jsonl`   | `{severity: 'high'\|'med'\|'low', location: 'path:line', claim: str, evidence_files: [str]}` per line; orchestrator emits one `--kind blocker` comment per finding. Read post-phase only, after DONE sentinel. |
| Merger       | `_orchestrator/merge_result.md`  | freeform markdown — "files resolved, strategy used". Posted as `--kind resolution` post-phase. |
| Any          | `_orchestrator/heartbeat.json`   | `{ts, last_progress, current_op}` — written by PostToolUse hook. Read live by the watchdog (not parsed for content, just `mtime`-checked). |
| Any          | `_orchestrator/DONE`             | sentinel per REQ-3b — `{"exit_status": "success"\|"error", "artifacts": [{"path": str, "sha256": str}]}` — written last. |

### Error handling approach

- **Schema-violating artifact**: orchestrator posts a `--kind blocker` comment ("worker N produced malformed `findings.jsonl` at line K"), transitions issue to `phase:implementing` (worker is treated as failed), and re-spawns.
- **Worker exits non-zero**: same path. Exit code recorded in `events.jsonl`.
- **Worker exits zero but produces no artifact**: same path. The orchestrator requires a `result.md` (Implementer) or `findings.jsonl` (Adversary, possibly empty) to consider the phase concluded.
- **Stale heartbeat**: REQ-11 path. Kill + cleanup + re-spawn.
- **`jj workspace add` collision (orphan from previous crash)**: spawn helper calls `jj workspace forget && rm -rf` unconditionally before `jj workspace add`. REQ-12.
- **`static_qa.sh` itself errors (not a tool failure but the script being malformed)**: orchestrator logs to `events.jsonl` with `kind=qa_script_error`, transitions issue to a poison state `phase:orchestrator-error`, refuses to advance it further, and a human must inspect. This is distinct from "QA tool returned non-zero" which is a normal blocker.
- **Crosslink CLI exit non-zero**: retry once with `--log-level debug`; if still failing, transition to `phase:orchestrator-error`.

### What the orchestrator does NOT do

- It does not run any `jj git push` or `gh` operation from *inside* a worker sandbox (REQ-5). It runs these from the project root only, during the landing step (REQ-17).
- It does not run a Refinement pump (REQ-16).
- It does not maintain its own hub branch, generate agent keys, or approve trust (REQ-18 — crosslink-layer).
- It does not parse or trust worker self-assessments of QA pass/fail (REQ-9).

## Open Questions

### Q1 (resolved): Build pump pickup policy = strict

The build pump picks up only issues labeled `phase:graphed`. No-phase issues are ignored entirely. The `/design` skill (or a human) applies `phase:graphed` as the explicit opt-in. Zero surprise; no ambiguity about whether refinement is "done".

### Q2 (resolved): Branch naming = `vdd/<id>-<short-slug>`

In both local and remote mode, the orchestrator's bookmark/branch for an issue is `vdd/<id>-<short-slug>`. The slug is derived from the issue title: lowercased, non-alphanumeric → `-`, collapsed runs of `-`, trimmed to ~40 chars at a word boundary. Example: issue #42 titled "Add batch retry logic for sync" → `vdd/42-add-batch-retry-logic-for-sync`.

### Q3 (resolved): Hooks sourced via the nix dev shell

The nix dev shell exposes crosslink's source tree (crosslink pinned via npins; REQ-1 + REQ-3a); `.claude/hooks/heartbeat.py` and `.claude/hooks/post-edit-check.py` are symlinks or generated wrappers pointing into that source. Updating crosslink (bumping the pin) automatically updates the hooks. No vendored copy, no submodule.

### Q5 (resolved): One Merger retry only

If the first Merger fails to produce a clean rebase/push, transition to `phase:awaiting-human-merge` and stop. No additional Merger spawns. The Merger had full conflict context fresh; repeating it almost certainly wastes inference.

### Q4 (resolved): Crosslink as Rust library

Crosslink is consumed as a Rust library dependency. REQ-3a captures the discipline: only documented-public crates are imported initially (tracker, signing, comment-write); any use of internal modules is flagged in review and tracked as technical debt. The crosslink pin is updated via an explicit issue.

## Out of Scope

- **Refinement pump** (was design.md phase 3). Humans drive refinement via `/design` and `crosslink subissue`. The orchestrator only consumes already-filed leaf issues with `phase:graphed`.
- **Cross-machine sync infrastructure** (was design.md phase 6). Crosslink's hub-branch replication keeps the local `issues.db` in sync; the orchestrator is multi-machine-oblivious. Hub-branch management, `crosslink agent init`, daemon setup, and trust approval are crosslink-layer responsibilities documented in the crosslink-guide, not here. (Note: the orchestrator DOES run `jj git push` and `gh pr create` during the landing step in remote mode — see REQ-17 — but this is per-branch code push, not the crosslink hub-sync machinery.)
- **Tree-shaped agent hierarchy with supervisors.** Flat per-issue is enough (design.md non-goal #1, preserved).
- **Replacing crosslink's tracker.** Crosslink is the substrate; the orchestrator only reads issues and writes comments through its CLI.
- **Judge mode and Human mode convergence.** Scoped in REQ-10 but not implemented in MVP or iteration 2. Adversary + n-rounds is the only convergence path that ships in this design's scope. Filed as a later issue once we have real workloads.
- **Container execution (Docker).** Crosslink offers it; the orchestrator uses `claude-sandbox` (bwrap) exclusively. No Docker path.
- **TUI / web dashboard for the orchestrator itself.** `crosslink tui` + `tail -f events.jsonl | jq .` + `jq . heartbeat-*.json` is the observability story (REQ-14).
- **Automatic human-merge resolution.** When the Merger fails (REQ-19 / AC-14), the orchestrator stops at `phase:awaiting-human-merge`. It does not retry indefinitely, escalate, or notify a paging system. Resumption requires an explicit human label (REQ-15a).
